# Style Guides.

In this markdown document, the style guide for each type of file in this repository is shown here.
When making a new document, don't forget to check this style guide or cross-reference another *correctly*-styled file.

Style guide does not need to be perfect, but it does need to be consistent enough.
If a new file is created with a previously undocumented style guide, notify Casper or find or create another style guide.
A style guide can not only differ on the file type, but also the intention (e.g. .pptx for a meeting or client.)

## Commits

When you want to push, add as many commit messages as possible;

If two or more files have been edited independantly of each other (e.g. Added additional style guide to style.md and added a learning goal to the cooperation contract.) Stage the changes, add commit messages, and commit them seperately of each other. If two or more files have been edited dependantly of each other (e.g. A MATLAB function was moved from one file to another; Fixed spelling errors across multiple files.), you must stage and commit them together.

Keep every file inside the repository.

Add a file to .gitignore if:

1. It is a test or temporary file.
2. It is not allowed to be uploaded.
3. It is generated by our programs and is not the final version.
4. You do not otherwise want to share it; Sharing is manditory if requested.

# .md

## style.md and other general .md files:

A .md file that is not excepted below follows the best practices format linked below.
They do not need to follow APA or IEEE standards, as long as they do use headings.

.md files should only be used when these conditions apply:
	1. They act as docstrings per folder, explaining the use of that folder.
	2. They are too short to justify word or LaTeX.

In such cases, they explain the purpose of that folder and the contents of each file.
If a file is not mentioned, it is assumed that there is nothing of direct importance contained within it.

[www.markdownguide.org/basic-syntax](https://www.markdownguide.org/basic-syntax/)

## structure.md:

Each folder and file should be seperated by goal, and be named accordingly.
Use camel case for file and folder names unless a local style guide overwrites it.

The file structure is order as follows, using unordered lists with an additional indent for each subfolder.
Files include their file extention and one additional indent with a single (full) sentence docstring.

- folder
  - subfolder
    - file.extension
      - file docstring

The first set of folders within the repository use headers.

## readme.md

**First heading**: Project Goal.
Explain what the goal of this repository is.

**Second heading:** User Manual
Explain to someone who has never visited this repository or viewed our project how to navigate and use the repository.

**Third heading:** Sources
readme does follow APA form and contains a collection of every single source used. In addition to APA form, each sources is referenced using IEEE form (using [#] marks inline.)

## plan.md

Use headers to seperate Finished -> Ongoing -> Planned.
Ongoing contains projects/tasks that have started, but not finished.
Planned contains concrete plans and tasks, and it contains rough ideas that are not final.
If an ongoing or planned task is assigned to a person, it is marked with **-name**.

Ask for or offer aid whenever possible. If you need anything from someone else, you must ask for it, and they must notify you of any progress made.
If they are finished, they need to schedule a session with you to explain how to use it, and you must explain in what form you need the results.

## .tex

Editable LaTex files are contained in their own folder under the same name.
Read only LateX files (or pdf's) are copied into the parent folder if it is in a finished state.

> There is currently no LaTeX style guide

## .py

We use PEP8. This can be found by opening the settings in the pylance addon and checking all boxes for the type checking mode.
In addition, each file has a docstring, then imports, and then the rest.
Each file that is not called main.py or enums.py only contains user defined functions or classes.

**Hard coded values are only allowed in testing** and<u>must immediatly be removed</u>after testing.
If certain values are common, expected or manditory, they must either exist as part of enums.py, default function values, or be entered when calling the function from main.py.

Python libraries are only allowed if they were used in any lecture by the proffessors (pandas, numpy, matplotlib.pyplot, scipy, etc) or if you can use them at least partially without the use of AI or documentation (itertools, typing, time, etc).

Use as few libraries as possible over the entire repository. If a library is used for certain functions which are also present in another library, use the other library instead. (If random and numpy are used, replace all instances of random with np.random.)

Define as many functions as necessary or more. As a rule of thumb: if your functions is greater than 10 lines of code or it uses at least one complicated calculation, seperate it into functions. If<u>ANY</u>calculation is useful or appears useful in more than one area or function, make it its own function.

If two or more lines of code are necessary for one "thing", add a comment. If 4-5 lines of code are necessary for one "thing" or you enter or leave a block (for, if, match, try, assert, etc), add an empty line.

## .m

Use Matlab Style guide by Richard Johnson as found in "Legal/styles/MatlabStyle2 book.pd" to the best of your ability.
